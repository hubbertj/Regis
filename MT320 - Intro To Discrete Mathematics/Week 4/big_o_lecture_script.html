This week we're really getting into some heavier, more useful topics. I'm going to break the outline into three videos, and the first is on big-O notation.

If you don't already know of big-O notation, it's pretty important. It helps us decide on which implementation of an algorithm is best, and to estimate how long algorithms and programs will take to run. These can show up in programming interviews, so it's a good idea to know this stuff.

We'll start with simple big-O examples. The 'O' stands for 'order' and we can think of it as 'this function costs on the order of x to run'. Big-O is an upper bound on how long something will take to execute (you can also use big-O to describe memory usage of a program, which isn't covered in this course). You might see it written like O(x), an italisized O(x) or with the fancy curly O.

Here's a simple example:

f(x) = x

The big-O runtime is O(x). Or O(x^2). Or O(x^3)...etc. Anything that takes longer to run than the function is technically a big-O runtime of the equation. When evaluating code or algorithms, it's typically best practice to pick the smallest reasonable big-O runtime rather than an arbitrary one. In the book he says this as 'The goal in using big-O notation to estimate functions is to choose a function g(x) as simple as possible, that grows relatively slowly so that f(x) is O(g(x)).'

I'm kind of a visual learner, so I like to look at these things as graphs. One easy and quick way to plot any equation is to use Wolfram Alpha. Here's an example of f1(x) = x and f2(x) = x^2: just type 'plot x and x^2' into the search bar on Wolfram. If you add 'from 0 to 10', it'll change the bounds on the plot. Hopefully we all know x^2 grows much faster than x, so that's why we can say x is O(x^2), but x^2 is not O(x). Plotting becomes more helpful as we introduce increasingly complex functions. I used Wolfram to plot functions in part of the homework.

In the book, the definition of big-O is a bit harder to understand, and it has the two constants k and C (called witnesses). This is fine for hardcore math, but for more practical programming, we typically assume x is going to infinity and constants don't matter. That's right, f(x) = 1000x and f(x) = 0.0001x are both O(x). This is probably partially because every company in a capitalistic society assumes infinite growth, so we have to plan for it. It also helps us gracefully scale to millions or billions of users. So that means for practical programming big-O runtimes, x is always greater than 0 (so k is 0), because we always have to go through the code execution at least once.

So now let's look at the Figure 3 in Chapter 3.2 of the book, which plots some common and important functions to know. So 1 is the fastest (always executes in one step) and n factorial (n!) is the worst, and there's a bunch in between. The logs are pretty much always base 2 in programming (because of binary bits that are 1 or 0). One possibly tricky one to remember is that any number to the nth power grows faster than n to any power (as we go to infinity). In the book this is n^c is O(d^n), but d^n is not O(n^c). Try plotting it on Wolfram if you're curious with c = 10 and d = 2. If you think about it, each time we increase n by 1, the exponent is increasing by 1. So infinity^1.1 is smaller than 1.1^infinity. In the book, this has the caveat d > c > 1, but I don't think that's correct, because 2^n grows much faster than n^2, and c=d in that case.

When we're looking at a function or an algorithm and trying to determine its order, we always find the fastest-growing term (as n or x approaches infinity). So for example, polynomials are dominated by their largest exponent: f(x) = x^3 + 500x is O(x^3).

What if we have something like f(x) = log(x^2) + x ? The order is x, because exponents in a logarithm don't matter. That's because we can move internal exponents in a log as a constant in front of the log. log(x^2) = 2log(x). However, the same is not true of external exponents like log(x)^2. So internal exponents in a log have to be factored in, but extenal exponents don't. This can make things tricky, like what is the runtime of log(x)^2 + x ? It's O(x). What about log(x)^3 + x ? It's log(x)^3. I only figured this out by plotting it on Wolfram.

Let me give you a few tips on the homework problems. The problems are scrambled so you may not have the same problem numbers as me or anyone else.

Find witnesses C and k: This one can be hard or easy; there are a couple ways to do it. The easier way is to plug in some values and test out the 'witnesses'. So for the k>1 options, you can plug in 1 and check for which values thing work out. For k>0, try plugging in 1/2. The much harder way is to modify the equations a bit using some common sense. The process goes like this: we know that fractions get smaller as the denominator grows, right? So we can drop the 1 from the bottom of the left equation and simplify things a bit. Then we can simplify again, getting rid of some x's. The we see we have 1/2x^2 + 1 < Cx^2, so the order x^2 makes sense at least. Then we do this trick I you'll see a few times in the homework, where we make every element in the equation the same highest-order function that we have as the order. So we end up with 1/2x^2 + 1x^2, and I'll leave the rest to you to conclude.

'Put the steps in order' problems, I first use language clues to narrow down my options. Anything with 'suppose' or 'consider' is almost always first, anything with 'hence' or 'therefore' is usually last, and things like 'then' and 'it follows' are usually in the middle. Once you have things narrowed down a bit, you'll have to go through the math in your head or on paper to verify the statements are correct, and put the intemediate steps in order.

finding the order of factored functions. Probably the best approach is the find the highest-order term in each set of parenthesis, and then multiply them to get the order. So for 13, is nlog(n) or n^2 greater? You may need to plot it, or if you think about it for a bit you may figure it out. n^3 vs 2 should be simple. So just multiply the 2 largest terms from each half, and you have your answer!

how many operations in one second?: This one is a bit tricky. Look at the hint, which will help. Then, what I did for the harder problems is type them into Wolfram Alpha to solve for me. For example, nlog(n) and one of the other answers, it's best to solve them numerically (i.e. iteratively, guess and check until we are close to the answer), so I just typed in 'solve n*log2(n) = 10^9' into Wolfram, and it spit out the answer. (There's also a way to solve nlog(n), but it's not easy). Watch out for the log2(n) vs log(n). log(n) is the default base-10 log, and log2(n) is base-2 log. If you've forgotten about logs, check out the definition on Wikipedia for a refresher. If you type 'nlog2(n)' without the *, it'll screw up the calculation, so check 'input interpretation' to make sure it looks right. For the rest of the parts to this problem, you can solve them by hand and then use a calculator (like Google) to crunch the numbers, or plug them straight into Wolfram.

bit string big-O: This was also a bit decieving at first, just go through the algorithm and start counting the steps. Look up what a bit string is if you don't know. Then start going through the string: the first element -- is it a 1 or a 0? That's an if statement, which is O(1). Next element - 1 or 0? And so on.
